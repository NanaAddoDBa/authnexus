# V0.1 Phase E — PostgreSQL Persistence

**Status:** Complete and accepted

## Outcome

Phase E gives each Phase D root a PostgreSQL adapter without starting authentication runtime work.
Repository and unit-of-work contracts live in `AuthNexus.Application`; EF Core, Npgsql, private row
records, mappings, adapters, destination encryption, and migrations live in
`AuthNexus.Infrastructure`. The six product modules remain free of database packages.

Infrastructure pins EF Core runtime, relational, and design packages to 10.0.11 and the Npgsql EF
Core provider to 10.0.3. The explicit relational reference keeps the API's transitive runtime
assembly on the same EF patch version used to compile Infrastructure.

The API still contains only its empty host. It does not call `AddAuthNexusPersistence`, open a
database connection, run migrations, resolve an application profile, change account state, verify
evidence, issue a session, emit an event, or enqueue a notification.

## Relational model

The initial migration is
`Persistence/Migrations/20260830190919_PhaseEInitialPersistence.cs`.

| Schema and table | Stored boundary | Declared database behavior |
| --- | --- | --- |
| `applications.application_profiles` | `ApplicationProfile` scalar values | UUID, vocabulary, non-blank, and version checks |
| `applications.application_redirect_uris` | Ordered redirect allowlist | Profile-owned FK with cascade delete; unique URI and sort position; deferred minimum-one-redirect triggers |
| `identity.user_accounts` | `UserAccount` lifecycle | State and timestamp checks; optimistic version token |
| `authentication.authentication_transactions` | Central transaction lifecycle | Purpose, state, expiry, terminal-shape, timestamp, and optimistic-version checks plus lookup indexes |
| `sessions.sessions` | Opaque-session verifier and lifecycle | Unique 43-character verifier hash, lifecycle checks, expiry indexes, and optimistic version token |
| `audit.security_events` | Immutable security activity | Fixed event/result vocabularies, JSON object metadata, query indexes, and update/delete/truncate rejection triggers |
| `notifications.outbox_messages` | Protected notification work | State-shape checks, due index, protected destination/payload columns, and optimistic version token |

EF records migration history in `infrastructure.__ef_migrations_history`. No cross-module foreign
keys were added. The redirect child table is the only current relational ownership relationship;
application, tenant, user, and session IDs in other schemas are contextual identifiers.

The redirect minimum is a transaction-level invariant. A profile and its first redirect can be
inserted in either order inside one transaction, but the deferred constraint triggers reject a
commit that leaves any profile without a redirect. They also cover child insert, update, delete,
and truncate paths declared by the migration. The child foreign key is deferrable and initially
deferred so the child-first order is real PostgreSQL behavior rather than a documentation claim.

`audit.security_events` has two protection layers. `AuthNexusDbContext` rejects tracked EF update or
delete operations for append-only records. The migration separately declares PostgreSQL triggers
that reject update, delete, and truncate statements. Event insertion remains available through
`ISecurityEventRepository.Append`.

## Repository operations

| Application port | Operations | Persistence behavior |
| --- | --- | --- |
| `IApplicationProfileRepository` | get, add | Redirect rows load with the profile; there is no update because the Phase D root has no mutation API |
| `IUserAccountRepository` | get, add, update | Rehydrates account state and carries the stored version back to updates |
| `IAuthenticationTransactionRepository` | get, add, update | Rehydrates the complete transaction lifecycle and uses optimistic versioning |
| `ISessionRepository` | get, add, update | Stores only `SessionSecretHash.EncodedValue`; no raw session secret exists in the row model |
| `ISecurityEventRepository` | get, append | Exposes no update or delete operation |
| `INotificationOutboxRepository` | get, get due, add, update | Orders due work by next-attempt time then ID and caps a requested batch at 500 |

Reads are no-tracking and rebuild domain objects through their public creation path or a narrow
internal restoration path. Invalid stored lifecycle combinations therefore fail rehydration rather
than producing partially valid domain objects. Repository writes only stage EF changes; they never
save independently.

## Concurrency and transaction boundary

`UserAccount`, `AuthenticationTransaction`, `Session`, and `NotificationOutboxMessage` rows use a
non-empty GUID `version` column as an EF concurrency token. A repository update supplies the version
observed by its earlier read. `AuthNexusDbContext` rotates the current version before saving and
translates `DbUpdateConcurrencyException` to `PersistenceConflictException` without exposing row
values in the message.

`IAuthNexusUnitOfWork.CommitAsync` saves all records staged in the scoped context.
`ExecuteInTransactionAsync` begins a PostgreSQL transaction, invokes the supplied operation, saves
the staged set once, and commits; exceptions roll the transaction back. This is the mechanism a
later workflow can use for a domain update, security event, and outbox insert. No Phase F or Phase J
workflow uses that combination yet.

## Notification destination protection

`NotificationDestination` is revealed only inside the Infrastructure protector. Before a row is
staged, it is encrypted with AES-256-GCM using a 12-byte random nonce and 16-byte authentication
tag. The stored envelope contains nonce, tag, and ciphertext; the row separately records the key ID
and format version. Associated data binds the envelope to its key ID, format, and
`NotificationOutboxMessageId`, preventing a valid destination envelope from being moved to a
different outbox row without authentication failure.

The key ring accepts base64-encoded 32-byte keys. `CurrentKeyId` selects the key for new writes;
older key IDs can remain in the ring for reads during rotation. Key bytes are cleared when the
singleton protector is disposed. Configuration is supplied to `AddAuthNexusPersistence`; product
code configures no runtime or production key, and no production key manager is selected in this
phase. Fixed keys under `tests/shared` are disposable test fixtures only.

The notification payload is already protected when the domain message is created. Phase E stores
those bytes and their separate key ID and format version without decrypting them.

## Composition and migration operation

`AddAuthNexusPersistence` registers one scoped `AuthNexusDbContext`, all six repositories, the
shared unit of work, and the singleton destination protector. The design-time factory reads only
`AUTHNEXUS_POSTGRES_CONNECTION`; it does not load `.env` automatically. Both runtime registration
and design-time tooling place the EF history table in the `infrastructure` schema.

Migration execution remains explicit. The API does not call `Database.Migrate` or
`EnsureCreated`. Acceptance applied, downgraded, and reapplied the migration only in randomly named
disposable databases. The durable local `authnexus` database and its Compose volume were not
changed.

## Defects closed during acceptance

The database tests found two defects that a successful build and generated migration script could
not reveal:

1. The redirect-cardinality triggers were deferred, but the redirect-to-profile foreign key was
   immediate. PostgreSQL therefore rejected a child-first transaction before the parent insert.
   The migration now alters `fk_application_redirect_uris_application_profiles` to
   `DEFERRABLE INITIALLY DEFERRED`, and tests execute both parent-first and child-first orders.
2. PostgreSQL treats a check expression that evaluates to `UNKNOWN` as satisfied. Terminal-shape
   equality such as `completed_at = state_changed_at` could therefore pass when `completed_at` was
   null. The authentication-transaction, session, and outbox constraints now use explicit
   `IS NOT NULL` requirements for every state-required lifecycle timestamp. Dedicated null-bypass
   regression cases cover each corrected branch.

The fixes are synchronized across the EF configurations, migration, migration designer, and model
snapshot. EF reports no pending model changes.

## Acceptance evidence

The final local acceptance run recorded:

- all 26 solution projects compiled in Release with zero warnings and zero errors;
- the 20-case integration project passed migration apply/history, downgrade/reapply, six-root
  round trips, four stale-writer conflicts, multi-record commit and rollback, context reuse, and
  due-query behavior;
- the 98-case security project passed every declared check constraint, redirect cardinality and
  ordering, audit immutability, recipient-at-rest protection, tamper detection, wrong and unknown
  key behavior, cross-row substitution rejection, and key rotation;
- the full backend run passed 571 of 571 tests across ten test projects, including both
  architecture rules;
- `dotnet ef migrations has-pending-model-changes` reported no drift;
- web type-check, lint, and production build passed;
- Compose interpolation and the PostgreSQL, Redis, and Mailpit behavioral checks passed; and
- the test cleanup audit found zero remaining `authnexus_test_*` databases.

The persistence suites use guarded, randomly named disposable databases. They did not apply the
migration to, truncate, reset, or delete the durable `authnexus` database or the `postgres-data`
volume.

This closes Phase E. Phase F is next but has not started. The Phase E database suites do not start
Phase M: Phase M remains the later whole-product integration, security, and end-to-end gate after
the runtime capabilities in Phases F through L exist.

## Explicitly not added

Phase E does not add identifiers, credentials, password hashes, OTP challenges, external providers,
passkeys, authentication orchestration, policy resolution, session-secret generation or
verification, cookies, middleware, product endpoints, seed users, Redis behavior, audit querying or
retention, an outbox claim/lease, a delivery worker, retry policy, provider adapters, receipts,
replay operations, automatic migration, backups, monitoring, or production deployment.
