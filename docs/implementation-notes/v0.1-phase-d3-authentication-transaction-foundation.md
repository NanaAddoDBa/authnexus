# V0.1 Phase D.3 — AuthenticationTransaction Foundation

**Status:** Complete

## Atomic task

Make the central authentication transaction a real in-memory domain boundary: identify one
interactive attempt, bind it to resolved application context and an explicit purpose, enforce its
lifetime, and allow only named state transitions. Do not introduce method verification,
challenges, policy/risk evaluation, sessions, persistence, audit storage, orchestration handlers,
or an authentication endpoint.

## Code boundary

`AuthNexus.Modules.Authentication` owns `AuthenticationTransaction`, its purpose/state enums, and
its lifecycle exceptions. `AuthenticationTransactionId` and `CorrelationId` live in the
dependency-free `AuthNexus.Domain` assembly because later challenge, session, audit, and outbox
models must be able to refer to the same attempt without referencing Authentication.

The only new production dependency is:

```text
AuthNexus.Modules.Authentication -> AuthNexus.Domain
```

Authentication consumes the already-shared `ApplicationId`, `TenantId`, and `UserId` values. It
does not reference the Applications or Identity modules that own those product boundaries.

## Stored transaction state

`AuthenticationTransaction.Create` accepts:

- a non-default transaction ID;
- a non-default application ID;
- an optional non-default tenant ID;
- an optional non-default user ID for workflows whose user is already known;
- one of the 14 declared purposes;
- a non-default correlation ID distinct from the transaction ID;
- a non-default creation timestamp; and
- a strictly later expiry timestamp.

Creation always produces `Initiated`. The aggregate exposes immutable context plus the controlled
lifecycle values below:

| Value | Rule |
| --- | --- |
| `TransactionId` | Identifies this attempt; never generated or replaced inside the entity. |
| `ApplicationId` / `TenantId?` | Captures already-resolved application context; no lookup occurs here. |
| `UserId?` | May identify an already-known user; D.3 provides no lookup, binding, or rebinding method. |
| `Purpose` | One declared purpose; the value does not enable the corresponding future capability. |
| `CorrelationId` | Stable cross-boundary correlation value; not a provider or session secret. |
| `State` | Starts `Initiated`; changes only through the seven named operations. |
| `CreatedAt` / `ExpiresAt` | UTC-normalized immutable half-open lifetime: `CreatedAt <= t < ExpiresAt`. |
| `StateChangedAt` | UTC time of the last accepted state transition; never moves backwards. |
| `CompletedAt?` | Set only by successful completion. |
| `FailedAt?` | Set only by terminal failure. Cancellation and expiry are not reported as failure. |

`StateChangedAt` is lifecycle bookkeeping, not an audit log. Later `SecurityEvent` work must still
record actor, reason, target, and security context atomically with persisted changes.

## Purpose vocabulary

The enum contains exactly the planned values, numbered from 1 through 14:

```text
SignIn                    Register
VerifyIdentifier          PasswordReset
LinkExternalIdentity      UnlinkExternalIdentity
EnrollPasskey             EnrollTotp
ChangeEmail               ChangePhone
ReplaceRecoveryMethod     SensitiveActionStepUp
AdminPolicyChange         AccountDeletion
```

Purpose-specific method visibility, assurance, expiry selection, authentication recency, audit
behavior, and session consequences are not implemented. D.3 validates the supplied purpose and
lifetime; it does not choose them.

## Legal transition graph

| Operation | Legal source state or states | Result |
| --- | --- | --- |
| `IssueChallenge` | `Initiated` | `ChallengeIssued` |
| `MarkPrimaryVerified` | `Initiated`, `ChallengeIssued` | `PrimaryVerified` |
| `RequireStepUp` | `PrimaryVerified` | `StepUpRequired` |
| `Complete` | `PrimaryVerified`, `StepUpRequired` | `Completed` |
| `Fail` | Any of the four live states | `Failed` |
| `Cancel` | Any of the four live states | `Cancelled` |
| `Expire` | Any of the four live states, at or after `ExpiresAt` | `Expired` |

The live states are `Initiated`, `ChallengeIssued`, `PrimaryVerified`, and `StepUpRequired`.
`Completed`, `Failed`, `Expired`, and `Cancelled` are terminal.

Direct `Initiated -> PrimaryVerified` supports a future method that produces verified evidence
without a separately persisted challenge. `Complete` from `StepUpRequired` records only lifecycle
progress; the later orchestration engine may call it only after verified evidence satisfies the
required assurance. D.3 itself neither receives nor evaluates that evidence.

There is no challenge resend self-transition and no `StepUpRequired -> ChallengeIssued` edge.
Future `AuthenticationChallenge` records own factor-specific issuance, resend, supersession,
attempt, and consumption state without erasing the transaction's primary-verification progress.

## Time and rejection rules

- Every supplied timestamp is required and normalized to UTC.
- `ExpiresAt` must be strictly later than `CreatedAt`.
- State-change timestamps cannot precede `StateChangedAt`.
- All non-expiry operations require `occurredAt < ExpiresAt`; at the deadline, expiry wins.
- `Expire` requires `occurredAt >= ExpiresAt`; early expiry is rejected.
- A rejected post-deadline operation does not silently mutate the entity to `Expired`. A later
  application service or expiry process must invoke `Expire` explicitly.
- Terminal-state validation occurs before elapsed-time handling. A transaction completed before
  its deadline remains completed rather than becoming expired later.
- State, `StateChangedAt`, `CompletedAt`, and `FailedAt` remain unchanged after every rejected
  state or time operation.

`InvalidAuthenticationTransactionStateTransitionException` reports the current and requested
states. `AuthenticationTransactionExpiredException` reports the configured expiry and attempted
operation time.

## Test contract

`AuthNexus.Modules.Authentication.Tests` contains 116 cases:

- 31 construction, context, identifier, lifetime, and fixed-purpose-vocabulary cases;
- all 18 legal state/action pairs;
- all 38 forbidden pairs from eight states multiplied by seven operations, excluding the legal
  pairs;
- all 14 legal non-expiry source/action pairs rejected exactly at the expiry boundary;
- early expiry rejected from all four live states;
- late expiry accepted from all four live states;
- all four terminal outcomes protected from retroactive expiry; and
- three transition timestamp cases for default rejection, non-decreasing chronology, and UTC
  normalization.

Every forbidden-pair test asserts the exception's current/requested states and snapshots all four
mutable lifecycle values before the call. The purpose test uses an explicit 14-value list rather
than deriving its expectation from the enum, so deleting or renumbering a required purpose fails
the suite.

## Deferred full-model fields

The central plan also names fields that depend on contracts not present in D.3:

| Deferred field | Why it is not represented as a placeholder |
| --- | --- |
| `RequestedReturnDestination` | Needs a shared validated destination contract; Authentication cannot reference Applications-owned `RedirectUri`, and raw request text would be unsafe. |
| `SelectedMethod` | Method registry and selection behavior do not exist. |
| `IdentifierHash` | Login-identifier normalization and hashing arrive with the identifier capability. |
| `RequiredAssuranceLevel` | The policy/assurance contract is Phase H work. |
| `AchievedAssuranceLevel` | Requires structured verified evidence. |
| `RiskResult` | The Risk module has no result contract or evaluator yet. |

These fields remain obligations of the central model. Deferring them prevents weak strings or
premature enums from becoming accidental long-term contracts.

## Capability boundary

D.3 creates no OTP, password, passkey, provider, or authorization-code data. It does not verify a
challenge, select a method, resolve a user, calculate assurance, score risk, issue a session,
validate a requested return destination, emit an audit event, or send a notification. There are no
repositories, EF Core mappings, migrations, concurrency tokens, clocks, ID generators, handlers,
dependency-injection registrations, API DTOs, routes, callbacks, or frontend transaction state.

The transaction can be constructed and exercised only by direct in-memory code today. D.4 begins
the `Session` domain foundation; Phase E begins persistence; Phase F will orchestrate this same
state model rather than introduce a second transaction architecture.
