# V0.1 Phase D.2 — UserAccount Foundation

**Status:** Complete

## Atomic task

Define the V0.1 account identity root and make its state machine executable. Do not introduce login
identifiers, credentials, persistence, audit storage, registration orchestration, policy checks,
administrative authorization, or an authentication endpoint.

## Code boundary

`AuthNexus.Modules.Identity` owns `UserAccount`, `UserAccountState`, and
`InvalidUserAccountStateTransitionException`. The shared `UserId` value belongs to
`AuthNexus.Domain.Identity` because future transactions, sessions, security events, and outbox
messages must refer to an account without taking a project reference on the Identity module.

The only new production dependency is:

```text
AuthNexus.Modules.Identity -> AuthNexus.Domain
```

Applications and Identity can both depend inward on Domain. They still cannot reference one
another or any other product module.

## Stored account state

A new account requires a non-default `UserId` and creation timestamp. It starts in
`PendingVerification`; callers cannot create an account directly as Active, Suspended, or Deleted.
The root exposes only four values:

- `UserId`;
- `State`;
- `CreatedAt`;
- `StateChangedAt`.

Creation and transition timestamps are normalized to UTC. A transition rejects a default timestamp
or a timestamp earlier than the previous state change, and a rejected call leaves both mutable
properties unchanged.

## Transition graph

```text
PendingVerification --Activate--------------------> Active
Active              --ProtectTemporarily----------> TemporarilyProtected
TemporarilyProtected--RestoreAfterProtection------> Active
Active              --Suspend---------------------> Suspended
Suspended           --Reactivate------------------> Active
Active              --RequestDeletion-------------> DeletionPending
DeletionPending     --CompleteDeletion------------> Deleted
```

Those are the only legal state/operation pairs. Every other pair throws
`InvalidUserAccountStateTransitionException`, which reports the current and requested states.
`Deleted` is terminal. D.2 intentionally provides no direct Active-to-Deleted operation, deletion
cancellation, arbitrary state setter, or collection of overlapping status booleans.

## Test contract

`AuthNexus.Modules.Identity.Tests` contains 46 cases:

- four creation/identifier cases;
- four lifecycle cases exercising all seven legal operations across activation, protection,
  suspension, and deletion;
- all 35 forbidden combinations from six states multiplied by seven operations, excluding the
  seven legal pairs;
- three timestamp cases covering UTC normalization, chronological ordering, and non-mutation after
  rejection.

The forbidden-transition matrix checks the exception's current/requested states and confirms that
neither `State` nor `StateChangedAt` changes. This prevents a later method-specific relaxation from
opening an unreviewed path while sample-based tests still pass.

## Security and audit boundary

Account activation, protection, suspension, reactivation, and deletion are security-sensitive.
The plans require audit output for those changes, but D.2 does not pretend that output exists. No
runtime or persistence path can call these methods today. The later SecurityEvent and persistence
work must commit the account update and its audit record atomically before account-state mutation
is exposed through an application or administrative workflow.

## Deferred

D.2 contains no email address, phone number, username, password, provider identity, passkey, TOTP,
recovery code, display profile, tenant/application membership, role, consent, or session data.
Optimistic concurrency, database rehydration, indexes, deletion retention/anonymization, suspension
reasons, protection reasons, authorization checks, and notification effects also remain deferred.
D.3 begins the `AuthenticationTransaction` domain boundary; Phase E begins persistence.
