# V0.1 Phase A — Repository Foundation

## Task record

```text
Version: V0.1
Phase: A — Repository foundation
Capability: Product source-of-truth and downstream-mirror boundary
Task: Establish the standalone AuthNexus repository and initial validation baseline
```

## Status

Complete. Phase A ends with a standalone source repository, an independently validated initial
downstream mirror, and an intentionally inactive automatic-sync boundary until its dedicated
least-privilege credentials are configured.

## Outcome

The standalone `NanaAddoDBa/authnexus` repository is established as the AuthNexus source of truth.
It contains the initial Next.js web scaffold, ASP.NET Core 10 solution and assembly boundaries,
test roots, engineering documentation, repository policies, release record, and standalone
validation workflow. The companion monorepo integration mirrors only an exact, standalone-CI-green
source revision into `apps/authnexus`; it is a downstream distribution surface, not a development
location.

## Why this task exists

AuthNexus needs a stable product boundary before it gains security-sensitive runtime behavior.
Creating that boundary first keeps future authentication capability slices independently testable,
versioned, and reviewable while preventing the broader monorepo from becoming a second source of
truth.

## Files and behavior changed

- Added the `apps/web` Next.js and `apps/api` ASP.NET Core 10 host scaffolds without implementing
  authentication routes or screens.
- Added `AuthNexus.Contracts`, `Domain`, `Application`, and `Infrastructure` assembly boundaries,
  plus a contract-name test.
- Added the `tests`, `docs`, `infra`, repository-policy, ADR, and release-record roots required for
  subsequent V0.1 work.
- Added standalone validation and an exact-SHA downstream-mirror dispatch definition. The dispatch
  is intentionally inactive until its dedicated cross-repository credential is configured.
- Defined the one-way Git-subtree/snapshot mirror boundary and exclusion of the source repository's
  `.github` directory from the monorepo mirror.

The only rendered web output is a truthful static foundation-status page. There are no
authentication, authorization, provider, session, persistence, or local-stack behaviors yet.

## Security considerations

No secrets, credentials, tokens, provider configurations, or real personal data are committed.
The source and target workflows require separate least-privilege credentials that are deliberately
external to version control. Source CI must succeed before it can request a mirror of its exact
commit SHA. The target mirror never pushes back to the source, never imports a nested Git
repository or submodule, and excludes source-level GitHub automation.

- `pnpm --dir apps/web lint` — passed.
- `pnpm --dir apps/web build` — passed; Next.js produced static routes for `/` and `/_not-found`.
- `dotnet restore AuthNexus.sln` — passed.
- `dotnet build AuthNexus.sln --configuration Release --no-restore` — passed with 0 warnings and
  0 errors.
- `dotnet test AuthNexus.sln --configuration Release --no-build` — passed: 1 test, 0 failures.

Hosted validation also passed for source revision `34f583114cb8c03f67d3865ad247dd26477be35b`:
the `Validate AuthNexus` workflow completed its `Frontend`, `Backend`, and exact-SHA downstream
dispatch jobs successfully. Its intended no-secret dispatch did not mark a target revision as
synchronized.

The monorepo integration pull requests passed their protected-branch pipeline and were merged.
The resulting `apps/authnexus/.source-revision` initially recorded
`34f583114cb8c03f67d3865ad247dd26477be35b`, with no nested Git repository, submodule, or source
`.github` directory. A manual run of the target synchronization workflow confirmed that a missing
target credential is reported as an explicit disabled state, leaves the recorded revision
unchanged, and does not create a false completion signal.

Standalone CI remains the authority for this mixed Next.js/.NET project. Phase A intentionally
does not add AuthNexus to the monorepo's Node/Go application deployment registry.

## Known limitations

- The cross-repository secrets `AUTHNEXUS_MIRROR_TOKEN` and
  `AUTHNEXUS_MONOREPO_SYNC_TOKEN` are not stored in this repository and must be configured by a
  repository administrator before automatic mirroring can run.
- There is no local Docker Compose stack, PostgreSQL/Redis implementation, migration, provider
  adapter, session, identity lifecycle, or operational deployment in this phase.
- The placeholder web page is not an authentication experience and must not be treated as one.
