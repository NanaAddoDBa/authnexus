# V0.1 Phase D.6 — Notification Outbox Foundation

## Outcome

D.6 adds the in-memory record for notification work that has been accepted for later delivery. The
record separates four facts that must not be collapsed into one boolean: the message is waiting,
it has been rescheduled after a failed attempt, it was delivered, or delivery has stopped
permanently.

This boundary does not make the outbox transactional. There is no table, unit of work, poller,
lease, provider call, or background process yet. Phase E must make the record durable, and Phase J
must prove that domain changes and outbox inserts commit together before any worker can deliver
them.

`NotificationOutboxMessage` belongs to `AuthNexus.Modules.Notifications`. That assembly references
only the dependency-free `AuthNexus.Domain` project for shared user, application, tenant, and
correlation identifiers. `NotificationOutboxMessageId`, channel, message type, destination,
protected payload, failure code, and delivery state remain Notifications-owned.

## Message envelope

`NotificationOutboxMessage.Create` accepts:

| Value | D.6 rule |
| --- | --- |
| `NotificationOutboxMessageId` | Required non-empty message identity. |
| `CorrelationId` | Required identity tying the future delivery record back to its originating workflow. |
| `TargetUserId?` | Optional intended user; a supplied default ID is rejected. |
| `ApplicationId?` | Optional consuming-application context; a supplied default ID is rejected. |
| `TenantId?` | Optional tenant scope; a supplied default ID is rejected. |
| `NotificationType` | Required lowercase ASCII machine code, capped at 100 characters. |
| `NotificationChannel` | One of `Email`, `Sms`, or `WhatsApp`. |
| `NotificationDestination` | Required trimmed destination, capped at 512 characters, with internal whitespace, control, separator, and Unicode formatting characters rejected. |
| `ProtectedNotificationPayload` | Required, non-empty protected bytes plus a protection-key identifier and positive format version. |
| `CreatedAt` | Required creation timestamp, normalized to UTC. |
| `AvailableAt` | Required first-attempt time at or after creation, normalized to UTC. |

Creation always starts in `Pending`. `StateChangedAt` equals `CreatedAt`, `AttemptCount` is zero,
`NextAttemptAt` equals `AvailableAt`, and no attempt, terminal timestamp, or failure code exists.

The optional user, application, and tenant identifiers are routing and incident context only. D.6
does not resolve them, authorize a recipient, select a template, infer a locale, or check whether
the originating account or application still exists.

## Destination and payload confidentiality

The destination remains an in-memory clear value because a later provider adapter must eventually
address the delivery. Ordinary consumers cannot read it through a public `Value` property:
`NotificationDestination` exposes only the deliberately named `RevealForDelivery()` operation and
always renders as `[notification-destination]`. Default JSON serialization therefore does not walk
into the email address or phone number. A future delivery adapter must opt in at the provider
boundary, where access can be reviewed and tested.

That is a diagnostic boundary, not at-rest encryption. Phase E must decide how recipient data is
stored and protected, and Phase J must prevent it from entering structured logs, traces, metrics,
failure text, or dead-letter inspection. D.6 only applies generic destination hygiene. The caller
must supply a destination already normalized and valid for the selected channel; email syntax,
E.164 phone rules, WhatsApp eligibility, and channel/destination compatibility remain later
contracts.

`ProtectedNotificationPayload` accepts bytes that a trusted future producer has already protected.
It makes defensive copies on both input and explicit delivery access, limits ciphertext to 65,536
bytes, records a bounded ASCII-safe protection-key identifier and positive format version, and
renders only `[protected-notification-payload:<length>]`. It neither encrypts nor decrypts data,
chooses a cryptographic algorithm, manages keys, serializes a template, nor claims that arbitrary
input bytes are actually ciphertext. Those responsibilities must be implemented before any
sensitive notification is persisted.

## Delivery state

The state vocabulary is explicit and one-based:

```text
Pending
RetryScheduled
Delivered
PermanentlyFailed
```

Only a delivery result changes state. D.6 deliberately has no `Processing` state or attempt lease;
without persistence and optimistic concurrency, either would imply a cross-worker guarantee that
does not exist.

| Current state | Operation | Result |
| --- | --- | --- |
| `Pending` | `RecordDelivered` | `Delivered` |
| `Pending` | `ScheduleRetry` | `RetryScheduled` |
| `Pending` | `FailPermanently` | `PermanentlyFailed` |
| `RetryScheduled` | `RecordDelivered` | `Delivered` |
| `RetryScheduled` | `ScheduleRetry` | `RetryScheduled` with a later due time |
| `RetryScheduled` | `FailPermanently` | `PermanentlyFailed` |

Those are the six accepted state/action pairs. The same three operations are rejected from each
terminal state, producing six forbidden pairs without mutation. `Delivered` and
`PermanentlyFailed` are terminal.

## Attempt and time rules

An attempt is due when `attemptedAt >= NextAttemptAt`; equality is accepted. The initial due time
is `AvailableAt`. A retry must be scheduled strictly after the failed attempt that produced it.
Every result timestamp is UTC-normalized, cannot precede the previous state change, and is fully
validated before any field changes.

Each accepted result records exactly one attempted delivery:

- `AttemptCount` increments once;
- `LastAttemptedAt` records the result time;
- `StateChangedAt` records the same time;
- retry retains a machine-readable `LastFailureCode` and establishes the next due time;
- permanent failure retains its machine-readable failure code, records `PermanentlyFailedAt`, and
  clears the schedule;
- delivery records `DeliveredAt`, clears the schedule, and clears the previous failure code.

The two terminal timestamps are mutually exclusive. Failure codes are bounded lowercase ASCII
machine codes, not provider error messages; rejected values are never copied into exception text.
Retry count limits, exponential backoff, jitter, provider-specific transient/permanent mapping,
dead-letter handling, and operator replay policy are Phase J decisions. D.6 records the outcome a
trusted caller supplies; it does not decide that outcome.

## Executable evidence

`AuthNexus.Modules.Notifications.Tests` passes 82 Release cases covering:

- strong message identity and fixed one-based state/channel vocabularies;
- required and optional context, including every supplied-default rejection;
- notification-type and failure-code normalization, character sets, and length limits;
- explicit destination reveal, redacted display/JSON output, length limits, embedded whitespace,
  control characters, Unicode separators, zero-width characters, bidirectional formatting,
  supplementary-plane formatting characters, and malformed surrogate input;
- protected-payload input/output copying, redacted display, size limit, key identifier, and format
  version;
- creation defaults, UTC normalization, and initial availability boundaries;
- due-time queries immediately before, exactly at, and after the deadline;
- all six accepted and six forbidden state/action pairs;
- retry sequencing, terminal exclusivity, attempt counts, failure-code handling, and successful
  delivery after retry;
- default, early, regressive, and invalid retry timestamps with complete mutable-state snapshots
  after rejection.

The focused Notifications suite builds and runs locally with all 82 cases passing. The exact
production dependency is `Notifications -> Domain`. Hosted Linux CI remains the acceptance
environment for the executable architecture check when Windows Application Control blocks a
copied assembly with `0x800711C7`; the security control remains enabled.

## Deliberately deferred

D.6 adds no:

- repository, EF Core mapping, migration, table, index, database transaction, or concurrency token;
- atomic write with an account, transaction, session, credential, policy, or audit change;
- worker, poller, claim/lease protocol, batch query, heartbeat, shutdown recovery, or node ownership;
- retry-count policy, backoff calculation, jitter, replay command, poison-message or dead-letter
  store;
- email, SMS, or WhatsApp provider adapter, provider request, delivery receipt, webhook, or status
  reconciliation;
- template catalogue, renderer, locale selection, sender identity, unsubscribe policy, or branding;
- encryption, decryption, key rotation, recipient-at-rest protection, or payload serialization;
- dependency-injection registration, application service, DTO, route, endpoint, or UI.

D.6 completed the six Phase D in-memory foundations. When this step was accepted, Phase E was next
and unstarted; no persistence work was included in the D.6 change. Current persistence status is
tracked in the V0.1 release ledger and the separate Phase E implementation record.
