# V0.1 Phase D.5 — SecurityEvent Foundation

## Outcome

D.5 adds the immutable event record used to describe security-relevant facts. It fixes the core
event vocabulary, separates event type from outcome, carries actor/target/application/tenant/session
context without module-to-module references, and gives metadata concrete defensive limits.

This is an append-oriented data boundary, not an event store. A constructed `SecurityEvent` has no
setters or lifecycle methods; a correction must eventually be another event. Phase E/I must still
prove append-only database behavior, transactional writes, redaction, querying, retention, and
authorization.

`AuthNexus.Modules.Audit` references only the dependency-free `AuthNexus.Domain` assembly. It uses
the shared `UserId`, `ApplicationId`, `TenantId`, `SessionId`, and `CorrelationId` values without
referencing Identity, Applications, Sessions, or any other product module. `SecurityEventId`
remains Audit-owned because no current cross-module contract consumes it.

## Event record

`SecurityEvent.Create` accepts:

| Value | D.5 rule |
| --- | --- |
| `SecurityEventId` | Required non-empty event identity. |
| `Timestamp` | Required and normalized to UTC. |
| `SecurityEventType` | One of the fixed 37 Plan 1 event types. |
| `SecurityEventResult` | One of the six declared D.5 outcomes. |
| `ActorUserId?` | Optional initiating user; a supplied default ID is rejected. |
| `TargetUserId?` | Optional affected user; may equal the actor. |
| `ApplicationId?` | Optional consuming-application context. |
| `TenantId?` | Optional tenant context; a supplied default ID is rejected. |
| `SessionId?` | Optional related session context. |
| `CorrelationId` | Required cross-boundary correlation identity. |
| `NetworkSummary?` | Optional pre-summarized, trimmed text capped at 256 characters. |
| `UserAgentSummary?` | Optional pre-summarized, trimmed text capped at 512 characters. |
| `SecurityEventMetadata` | Required immutable metadata object; it may contain zero entries. |

Optional `TenantId` is an explicit AuthNexus extension to Plan 1's event-field list. D.1 placed the
tenant identifier in the shared Domain assembly for later transactions, sessions, and audit. An
audit record without the already-resolved tenant scope would weaken cross-tenant incident review.
The field does not infer or authorize a tenant.

Network and user-agent values must already be summarized by a future trusted builder. D.5 does not
read request headers, store a raw IP address, infer location, fingerprint a device, or define a
privacy-retention policy.

## Fixed event catalogue

The enum is one-based and maps to these exact machine codes:

```text
registration_requested             registration_completed
email_verification_sent            email_verified
phone_verification_sent            phone_verified
login_succeeded                     login_failed
login_throttled                     mfa_required
mfa_succeeded                       mfa_failed
password_reset_requested            password_reset_completed
password_changed                    passkey_added
passkey_used                        passkey_removed
totp_added                          totp_removed
recovery_code_used                  external_identity_linked
external_identity_unlinked          session_created
session_revoked                     logout_all
security_step_up_required           security_step_up_completed
account_temporarily_protected       account_suspended
account_deletion_requested          account_deleted
authorization_denied                policy_draft_created
policy_changed                      policy_approved
provider_unavailable
```

Declaring a code does not claim that its future workflow or emitter exists. No D.1-D.4 operation
automatically creates an event yet.

## Result vocabulary decision

Plan 1 requires a separate `Result` field but does not define its values. D.5 records this explicit
six-value AuthNexus decision:

```text
Succeeded
Failed
Denied
Throttled
Cancelled
Informational
```

D.5 does not impose an event-type/result compatibility table. Compatibility is delegated to
future typed emitters in the later orchestration and policy phases; adding a guessed table now
could reject valid facts or legitimize incorrect ones. The current result tests prove only that
the literal vocabulary remains fixed and each value can be recorded, not that every possible
event-type/result pair is semantically valid.

## Metadata contract

`SecurityEventMetadata` makes a defensive copy and exposes a read-only dictionary. It enforces:

- at most 32 entries;
- keys of at most 64 characters, starting with an ASCII letter and using only lowercase ASCII
  letters, digits, `.`, `_`, or `-` after normalization;
- values of at most 512 trimmed characters;
- no null or blank key/value;
- no duplicates after key normalization;
- no control, Unicode line/paragraph separator, or bidirectional/format characters;
- no explicit or separator-delimited sensitive key material such as `password`, `otp`, `secret`,
  `token`, `seed`, `recovery.code`, or `authorization.code`.

The sensitive-key rule covers nested forms such as `request.password`, `password.value`,
`otp.code`, `otp_code`, and `reset.token`, not only a short exact-name list. Exceptions never echo
the rejected value, and metadata display reports only its entry count.

This remains a guardrail, not a redaction proof. A caller could hide a secret under an innocent key
such as `detail`. Phase I must centralize event construction and test the serialized database and
structured-log output against the complete prohibition list: passwords, OTPs, reset tokens,
session secrets, OAuth authorization codes, refresh tokens, TOTP seeds, and recovery codes.

## Executable evidence

`AuthNexus.Modules.Audit.Tests` passes 107 Release cases covering:

- strong event identity and UTC timestamp normalization;
- the literal one-based 37-type catalogue and every exact snake-case code;
- the literal one-based six-result vocabulary;
- minimal and complete event context, including every optional-default rejection;
- same-user actor/target records;
- summary trimming, length limits, control characters, Unicode separators, and bidi formatting;
- null, blank, malformed, duplicate, oversized, and over-count metadata;
- all explicit and separator-delimited sensitive-key bypasses;
- source-collection copying and read-only exposure;
- non-leaking validation errors and the absence of public event setters.

The focused Audit suite builds and runs locally with all 107 cases passing. The exact production
dependency is `Audit -> Domain`. Hosted Linux CI remains the acceptance environment for the two
architecture cases when Windows Application Control blocks a copied module assembly with
`0x800711C7`; the security control is not disabled.

## Deliberately deferred

D.5 adds no:

- repository, EF Core mapping, migration, table, index, update/delete policy, or database trigger;
- audit writer, cross-module emitter, application service, or atomic state/event commit;
- serializer, central redaction pipeline, structured-log sink, SIEM exporter, or alert rule;
- query, filter, pagination, retention, erasure exception, administrative endpoint, or UI;
- network/user-agent parser, geolocation lookup, device fingerprint, telemetry, or metric;
- dependency-injection registration, DTO, route, or host behavior.

The next and final Phase D boundary is D.6: `NotificationOutboxMessage` and its delivery-state
invariants. D.5 does not start persistence or delivery processing.
