# V0.1 Phase D.4 — Session Foundation

## Outcome

D.4 adds the in-memory record that will eventually sit behind an opaque browser-session cookie.
It gives AuthNexus one session identity, one stored verifier representation, and explicit rules for
activity, verifier rotation, revocation, and expiry. It does not issue a browser credential or make
the API recognize one.

The production boundary is `AuthNexus.Modules.Sessions`. Its only direct project dependency is the
dependency-free `AuthNexus.Domain` assembly. The shared `SessionId` lives under
`AuthNexus.Domain.Sessions` because the D.5 audit record needs to refer to a session without
referencing the Sessions module.

## Stored session data

`Session.Create` requires:

| Value | D.4 rule |
| --- | --- |
| `SessionId` | Strong, non-empty identifier. It is record identity, never a bearer credential. |
| `SessionSecretHash` | An unpadded base64url-encoded 32-byte digest. No raw session secret is accepted. |
| `UserId` | Required account identity. D.4 performs no account lookup. |
| `ApplicationId` | Required application scope. D.4 performs no application lookup. |
| `TenantId?` | Optional tenant scope; a supplied default ID is rejected. |
| `AuthenticatedAt` | Required authentication timestamp at or before record creation. |
| `CreatedAt` | Required record-creation timestamp and initial lifecycle timestamp. |
| `IdleExpiresAt` | Strictly later than creation and no later than absolute expiry. |
| `AbsoluteExpiresAt` | Strictly later than creation and never extended by the entity. |

Creation always starts in `Active`. `LastSeenAt`, `UpdatedAt`, `StateChangedAt`, and
`SecretRotatedAt` initially equal `CreatedAt`; `RotationCount` is zero; terminal timestamps and the
revocation reason are absent. All timestamps are normalized to UTC.

Optional `TenantId` is an AuthNexus D.4 extension to Plan 1's abbreviated session-record list. The
application profile and transaction already carry optional tenant context, and omitting it from
the durable session identity would leave a cross-tenant authorization ambiguity later. This field
does not resolve a tenant or authorize access by itself.

## Stored verifier boundary

`SessionSecretHash` accepts exactly 43 unpadded base64url characters, the canonical encoded size of
a 32-byte digest. Its `ToString` output is always `[session-secret-hash]`. The entity accepts and
returns no raw cookie value, and it cannot generate, hash, compare, or transport a bearer secret.

The fixed representation is a persistence-facing verifier contract, not proof of cryptographic
session issuance. Phase G must still generate a high-entropy secret, derive the stored value,
compare it safely, set the cookie, rotate the browser credential, and invalidate the old one.

## State and lifetime

The D.4 state vocabulary is deliberately small:

```text
Active
Revoked
Expired
```

The usable interval is half-open:

```text
CreatedAt <= observedAt < min(IdleExpiresAt, AbsoluteExpiresAt)
```

`CanBeUsedAt` evaluates both state and timestamps without changing the entity. A cleanup worker is
therefore not required to run before an elapsed session becomes unusable. The stored `Expired`
state remains useful for an explicit lifecycle record, but it is not the security boundary by
itself.

## Operations

| Operation | Required state | Effect |
| --- | --- | --- |
| `RecordActivity` | `Active`, strictly before effective expiry | Advances `LastSeenAt`; accepts an idle deadline that does not shorten the current one or exceed absolute expiry. |
| `RotateSecretHash` | `Active`, strictly before effective expiry | Replaces the verifier with a distinct hash, increments `RotationCount`, and records `SecretRotatedAt`. |
| `Revoke` | `Active` | Moves to `Revoked` and records the first timestamp and machine-readable reason. |
| `Revoke` | `Revoked` | Idempotent no-op; preserves the original timestamp and reason. |
| `Expire` | `Active`, at or after effective expiry | Moves to `Expired` and records `ExpiredAt`. |

Across three states and four operations, five state/action pairs are accepted and the other seven
are rejected. `Revoked` and `Expired` are terminal except for the deliberate repeated-revocation
no-op. That no-op supports safe repeated logout or revocation requests without erasing the reason
that first removed access.

Activity and rotation use the same half-open deadline as `CanBeUsedAt`. At the exact effective
expiry they throw `SessionExpiredException` and leave every field unchanged. `Expire` is rejected
one tick before the deadline and accepted exactly at it. A revoked record is never rewritten as
expired merely because time passes.

Revocation is allowed for an `Active` record even when its timestamps have already elapsed. This is
an explicit fail-closed D.4 decision: revocation only removes access and may carry a security or
administrative reason worth preserving. Activity and rotation remain prohibited after expiry.

Every accepted operation uses caller-supplied UTC-normalized time and cannot precede the previous
accepted operation. Validation completes before mutation. A rejected operation cannot partially
change state, hash, deadlines, counters, terminal data, or lifecycle timestamps.

## Revocation reasons

D.4 uses ten one-based machine reasons instead of arbitrary prose:

```text
UserLogout             UserRevoked
LogoutAll              CredentialReset
SecurityStampChanged   AccountProtected
AccountSuspended       AccountDeletion
AdministratorRevoked   SecurityIncident
```

These values describe why access was removed. They do not perform logout-all, credential reset,
security-stamp comparison, account-state synchronization, or administrative authorization.

## Executable evidence

`AuthNexus.Modules.Sessions.Tests` contains 65 cases covering:

- strong session identity and canonical, redacted hash representation;
- required and optional application, tenant, and user context;
- every construction timestamp and lifetime boundary;
- fixed one-based state and revocation-reason vocabularies;
- half-open idle and absolute lifetime checks without mutation;
- successful activity extension and the absolute cap;
- exact-deadline activity and rotation rejection;
- distinct-hash rotation and counter behavior;
- revocation, elapsed-record revocation, and repeated-revocation idempotency;
- early, exact, and late explicit expiry;
- all five legal and seven forbidden state/action pairs;
- terminal precedence, global timestamp monotonicity, and full mutable-state snapshots after
  rejection.

The focused Release suite initially passed 62 cases; the canonical base64url pad-bit review added
two rejection cases and an explicit absolute-deadline transition case, bringing the final matrix
to 65. The final hosted Release run is the
acceptance result after the Windows host began blocking copied assemblies. The architecture
project compiles with the new
`Sessions -> Domain` edge. On the Windows development host, Application Control then blocks the
architecture test assembly from loading with `0x800711C7`; the control remains enabled, and hosted
Linux CI is the acceptance environment for executing that two-test suite.

## Deliberately deferred

Plan 1's complete session record also names last reauthentication, authentication level and
methods, MFA satisfaction, device label, user-agent summary, and approximate network metadata.
Those fields wait for the Phase F evidence model, Phase H assurance contract, and privacy-aware
normalization rules instead of being frozen as strings or unverified booleans in D.4.

D.4 adds none of the following:

- random secret generation, digest derivation, verifier comparison, or key management;
- cookie creation, `Secure`/`HttpOnly`/`SameSite` transport, or anonymous-session replacement;
- authentication handlers, middleware, lookup, ownership checks, logout services, or list APIs;
- security-stamp integration, cross-node revocation propagation, or Redis consumers;
- evidence evaluation, assurance upgrade, device/network collection, audit emission, or outbox
  messages;
- repositories, EF Core mappings, migrations, database constraints, or concurrency handling;
- dependency-injection registration, API DTOs, routes, endpoints, or frontend session state.

The next Phase D boundary is D.5: an immutable `SecurityEvent` record. D.4 does not start it.
